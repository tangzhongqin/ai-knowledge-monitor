# 🔄 Loop 工程详解

> 来源：抖音 @AI 费曼学习法（第 01/05 集）| 收集时间：2026-07-23

---

## 📌 一句话总结

Loop Engineering（循环工程）是 AI 工具进化的终局形态 —— 从 Chatbot 到 Prompt 到 Context 到 Harness，最终到达 **尽量无人参与的自动化 Loop**，它是让 AI 从"工具"变成"生产力系统"的关键跨越。

---

## 🔍 核心内容

### Loop 是什么？

Loop Engineering 直译为"循环工程"。Loop 不是新概念 —— 生活中的洗衣机洗衣模式、变频空调根据室温自动调节功率，本质上都是预设好的 Loop。

但在 AI 领域，Loop 经历了**四次跃迁**才到达今天的形态：

```
Chatbot 时代 → Prompt 时代 → Context 时代 → Harness 时代 → Loop 时代
   （聊天）     （提示词）    （上下文）      （约束引导）    （循环工程）
```

### 四次跃迁详解

**第一次跃迁：Chatbot → Prompt（提示词时代）**
- AI 刚诞生时，人们只把它当聊天机器人，没有生产力
- 后来发现：给 AI 清晰明确的指令，它就能产生有价值的结果
- 核心公式：**你的提示词质量越高，AI 回答质量越高**
- 这时期的 Loop 是最基础的形式：你问 → AI 答 → 你看 → 不满意就让它改

**第二次跃迁：Prompt → Context（上下文时代）**
- 基础 Loop 的巨大缺陷：**AI 会失忆**
- 这不是设计缺陷，而是大模型本质无状态 —— 它不记得任何曾经发生过的事
- 过了几轮对话，或者换个会话，它就什么都不记得了
- 解决方案：上下文工程（Context Engineering），让 AI 拥有"记忆"

**第三次跃迁：Context → Harness（约束引导时代）**
- 有了上下文还不够，AI 仍然可能犯错、做不该做的事
- Harness 本意是"束带"，引申为**约束和引导 AI 产出更高质量工作**
- 通过规则、边界条件、验收标准来框定 AI 的行为空间

**第四次跃迁：Harness → Loop（循环工程时代）**
- 为了极大提高 AI 的生产效率，正式进入 Loop 时代
- 关键区别：前三次的 Loop **都有人作为重要参与者**；而当前的 Loop 追求的是**尽量减少人参与，甚至无人参与的自动化循环**

### 四种 Loop 类型

| 类型 | 触发方式 | 典型场景 |
|------|----------|----------|
| **回合制** | 用户发起一轮交互 | 问→答→检查→修正，传统 Chat 模式 |
| **目标制** | 设定目标后自动运转 | Agent 接到任务后自主规划、执行、验证 |
| **定时制** | 按时间计划触发 | 定时报告、定时检查、定时同步 |
| **主动制** | AI 自主感知并触发 | 监控到异常自动发起处理流程 |

### 一个比喻理解全貌

用"老板（你）招聘清华实习生小张（AI）"来理解四阶段：

- **Chatbot 时代的小张**：刚来店里，什么都不知道，只能聊天，什么都干不了
- **Prompt 时代的小张**：你给他清晰指令"小张，去把货架收拾干净"，他就能干活了
- **Context 时代的小张**：你昨天交代过的事情，他今天还记得；你家的商品信息、仓库布局他都了然于胸
- **Harness 时代的小张**：他不会擅自打折、不会乱承诺客户、一切按你的规矩来
- **Loop 时代的小张**：你只需要说"这个月销量提升 10%"，他自己规划、执行、汇报、调整，你只看结果

## 🧠 专家升华

### 一、技术深度分析：Loop 的工程本质

Loop Engineering 在工程上解决的是**AI 系统的控制流问题**。

传统 Prompt Engineering 关注的是**单次调用的输入质量**，而 Loop Engineering 关注的是**多次调用的编排和反馈闭环**。从架构视角看，一个完整的 Loop 系统需要三个组件：

```
┌─────────────────────────────────────────────┐
│                  Loop Engine                  │
│                                              │
│  ┌──────────┐    ┌──────────┐    ┌─────────┐ │
│  │ Planner  │───▶│ Executor │───▶│ Judge   │ │
│  │ 规划器   │    │ 执行器   │    │ 评判器  │ │
│  └──────────┘    └──────────┘    └─────────┘ │
│       ▲                               │      │
│       └───────── 反馈循环 ────────────┘      │
└─────────────────────────────────────────────┘
```

- **Planner（规划器）**：将模糊目标分解为可执行步骤。对应 Claude Code 的"读项目、拆需求、定方案"
- **Executor（执行器）**：按步骤执行具体操作。对应 Codex 的"写代码、改文件、跑命令"
- **Judge（评判器）**：检查结果是否符合预期，决定是继续迭代还是结束。这是 Loop 质量的核心
- **Memory（记忆层）**：贯穿始终 —— 没有记忆的 Loop 等于没有 Loop

这与 LangChain 的 AgentExecutor、AutoGPT 的思考-执行-观察循环、以及 Anthropic 的 Computer Use Agent 在架构上高度一致。**Loop Engineering 不是新概念，而是对 Agent 架构核心模式的重新命名和系统化。**

### 二、行业位置：为什么现在 Loop 火了

Loop 成为热词，有三个时代背景：

1. **模型能力到位了**：GPT-4/Claude 4 级别的模型才能真正理解复杂指令并在多轮循环中保持一致。两年前的模型无法支撑有意义的 Loop。
2. **工具链成熟了**：Claude Code 的 sub-agent、Codex 的 Record & Replay、MCP 协议 —— 这些基础设施让"编排多个 AI 调用形成 Loop"从手工活变成了工程活。
3. **成本降到临界点**：一次复杂 Loop 可能涉及几十次模型调用。只有当推理成本降到足够低，Loop 才有商业可行性。

**在 AI 工具链的定位**：Loop Engineering 处于最上层，它调用 Prompt Engineering（单轮质量）、Context Engineering（记忆管理）、Harness Engineering（约束规则）作为基础设施。如果 Prompt/Context/Harness 是"零件"，Loop 就是"生产线"。

### 三、更优方案：从理论到实操

**当前最实用的 Loop 落地方式**（基于 2026 年 7 月的工具生态）：

**方案 A：Claude Code 原生 Loop**
```
Claude Code 的 sub-agent + worktree + MCP 工具 = 内建 Loop
- Planner: Claude Code 主 Agent 读项目、拆任务
- Executor: sub-agent 执行具体任务（每个 sub-agent 内部还有 Loop）
- Judge: Claude Code 自动检查 diff、运行测试
- 适合：单仓库开发任务
```

**方案 B：Claude Code + Codex 联合 Loop**（见本文姊妹篇《ClaudeCode+Codex 最稳分工法》）
```
Claude Code 规划 → Codex 执行 → Claude Code 验收 → Codex 修正 → 循环
- 优势：Codex 执行速度快、操作桌面应用能力强
- 劣势：需要手动衔接，Loop 不自动闭合
```

**方案 C：n8n 可视化 Loop**
```
n8n 工作流节点串联，定时触发 + 条件分支 + AI 节点
- 适合：定时制 Loop（日报生成、数据同步、监控告警）
- 优势：零代码、可视化、稳定可靠
```

**方案 D：自主 Agent Loop（实验性）**
```
LangChain/LlamaIndex Agent + Tool Calling Loop
- 优势：完全自主、无人参与
- 风险：可能失控、成本不可控、需要严格 Harness 约束
```

**推荐路径**：从方案 A 入门（Claude Code 原生 Loop）→ 用方案 B 处理跨工具场景 → 用方案 C 固化高频定时任务 → 谨慎尝试方案 D。

### 四、实操建议：设计一个好的 Loop

1. **先定义终点，再设计循环**：Loop 是围绕目标转的。目标不清晰，Loop 就是死循环。
2. **每一次迭代必须有"信息增益"**：每轮 Loop 应该让 AI 更接近目标，而不是原地踏步。如果 Loop 在同样的问题上来回打转，说明 Judge 组件失效了。
3. **设置硬性退出条件**：最大迭代次数、超时时间、明确完成标准 —— 三者至少设置两个。
4. **人的位置要精确**：什么时候需要人介入？是每个 Loop 结束时？还是只在异常时？**人参与的节点越少，系统效率越高；但完全不设人的开关，风险也越大。**
5. **日志和回放至关重要**：每个 Loop 的输入、输出、决策理由必须记录。Codex 的 Record & Replay 功能本质上就是 Loop 日志的极致应用。

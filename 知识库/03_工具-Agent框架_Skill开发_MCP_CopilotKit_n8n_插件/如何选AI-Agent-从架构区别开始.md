# 如何选择 AI Agent —— 从架构区别开始

> 来源：抖音 @老林 / 2026-07-23 / 系列第一期

---

## 📌 一句话总结

AI Agent 架构可以按能力演进分为**执行 -> 推理 -> 协作 -> 进化**四大层级，九种具体架构。选型核心原则：架构复杂度必须与任务复杂度匹配——能一个人干的活别组团队，真需要协作时别让一个人硬扛。当前编程类 Agent 几乎全部走向 Multi-Agent 或 Router+Skill 架构，而 Workflow 在标准化场景中仍然不可替代。

---

## 🔍 核心内容

### Agent 架构四大层级、九种模式全景图

#### 第一层：基础执行层（解决"怎么做"）

**1. 单 Agent 架构（Single Agent）**
- **形态**：一个模型从头干到尾，理解、规划、调用工具、执行全包
- **优点**：简单、轻量、好部署
- **缺点**：能力有上限，复杂或长任务扛不住
- **典型案例**：早期 ChatGPT 插件模式

**2. Workflow 架构（工作流）**
- **形态**：将任务拆成固定的流水线，一步一步往下走
- **优点**：流程清晰、可控、好审计
- **缺点**：灵活性不足，环境一旦变化就无法应对
- **典型案例**：ComfyUI（做图做视频的节点式编排工具）

> **小结**：这两种架构解决的是"怎么做"的问题，能力上限明显，适合流程固定、环境稳定的简单任务。

#### 第二层：动态推理层（解决"怎么想"）

**3. ReAct 架构（Reasoning + Acting）**
- **形态**：核心是一个动作循环——思考 -> 行动 -> 观察 -> 再思考 -> 再行动 -> 再观察
- **本质**：边做边看，看到结果再决定下一步
- **优点**：灵活适应、可解释性强（能看到每一步在想什么）
- **缺点**：多步任务反复调用模型导致延迟高、成本高，偶尔陷入死循环
- **擅长**：动态应变

**4. Plan & Execute 架构（先想后做）**
- **形态**：先用"规划器"列出完整任务计划，再交给"执行器"按计划逐步执行
- **优点**：全局视野好、步骤清晰、不容易跑偏、可并行执行
- **缺点**：环境变化时无法临时调整、提示词成本高
- **擅长**：全局规划

> **小结**：这两种架构解决的是"执行任务时怎么想"——ReAct 擅动态应变，Plan & Execute 擅全局规划。

#### 第三层：分工协作层（解决"怎么合作"）

**5. 多 Agent 架构（Multi-Agent）**
- **形态**：多个角色不同的 Agent 协作完成复杂任务。可以是"主管指挥多个专员"（层级制），也可以是"对等协调"（联邦制）
- **优点**：扩展性强、容错性好、支持超长上下文
- **缺点**：系统复杂度飙升、协调开销大、调试非常头疼
- **擅长**：协调

**6. Router + Skill 架构（路由 + 技能）**
- **形态**：一个路由 Agent 当调度员，根据请求动态选择并调用不同的技能模块
- **特点**：Skill 可插拔、可复用、按需加载、节省上下文窗口
- **优点**：易于扩展和维护、节省上下文窗口
- **缺点**：路由准确性是关键瓶颈（分错技能 = 全盘皆输）
- **典型案例**：Claude Code 的 Skill 机制——只在需要时加载对应技能指令

**7. Blackboard 架构（黑板模式）**
- **形态**：多个 Agent 不直接通信，而是往一块共享"黑板"上写中间结果，谁看到谁能干就接着干
- **优点**：松散耦合、支持异步协作、易于扩展
- **缺点**：并发控制困难、数据一致性一直是难题
- **擅长**：异步松散环境下的协作

> **小结**：这三种架构解决的是"Agent 怎么合作"——Multi-Agent 擅协调，Router+Skill 擅调度，Blackboard 擅异步松耦合协作。

#### 第四层：自我进化层（让 Agent 学会复盘）

**8. Reflection 架构（反思）**
- **形态**：任务执行完后加上一个自我反思环节——Agent 评估自己的输出，发现错误就修正，把经验存入记忆
- **本质**：相当于给 Agent 配了一个"复盘"过程
- **效果**：代码生成、数学推理准确率提升非常明显
- **关键**：不是独立架构，而是可叠加的增强模块

**9. 思维树架构（Tree of Thoughts）**
- **形态**：把推理变成搜索问题——不再一条路走到黑，而是同时探索和评估多条路径，最终选最优方案
- **本质**：相当于给 Agent 配了一个"参谋部"，遇到复杂决策先做沙盘推演
- **关键**：不是独立架构，而是可叠加的增强模块

> **小结**：Reflection 和 Tree of Thoughts 是增强模块，可以叠加到任何基础架构上——给单 Agent 加反思，给多 Agent 加思维树，都成立。

---

### 从执行到进化：Agent 架构演进的本质

```
执行 -> 推理 -> 协作 -> 进化
确定 -> 涌现 -> 单兵 -> 协作 -> 学会复盘
```

**本质洞察**：用工程的复杂性，去补偿当前大模型在知识、记忆和推理上的不足。

---

### 按场景选架构：编程类 Agent 的实践验证

| 场景 | 主流架构选择 | 原因 |
|------|------|------|
| **编程类 Agent**（Claude Code, Codex, Cursor, Trae/Coder） | Multi-Agent 或 Router+Skill | 编程天然需要分工——理解需求、写代码、测试、审查各有专攻 |
| **通用写作/Agent 平台**（OpenCloud, Workbody 等） | Multi-Agent + Router 混合 | 既要处理不同类型任务，又要多 Agent 协作完成复杂工作流 |
| **标准化流程任务**（做图/做视频） | Workflow | 流程固定的任务中，确定性和可控性的优势不可替代 |

**Workflow 并没有死**：ComfyUI 已经证明，在流程确定、质量要求高、需要精确复现的场景中，Workflow 带来的确定性和可审计性，是纯 Agent 方案至今做不到的。

---

### 选型总原则

> **架构复杂度要匹配任务复杂度。能用一个人干的活别组团队，但真需要多人协作时也别让一个人硬扛。**

## 🧠 专家升华

### 一、技术深度分析：各架构的底层机理

#### ReAct 的死循环问题与解法

ReAct 陷入死循环的根因通常是三个：
1. **观察信号太弱**：执行结果不包含足够信息让模型判断"进展如何"
2. **缺乏时间感知**：模型不知道已经迭代了多少轮
3. **终止条件模糊**：模型不知道什么时候算"完成"

**工业级解法**：
- **步数硬限制**：设置 max_steps，超限强制终止或升级给人类
- **评估器介入**：每 N 步引入一个独立的"裁判模型"评估进度
- **结构化观察**：不只把工具输出丢回去，而是附加元信息（如"这是第 5 步 / 最多 20 步"）
- **ReAct + Plan 混合**：先用 Planner 设定边界，再用 ReAct 在边界内灵活执行

#### Plan & Execute 的僵化问题

Plan & Execute 的致命弱点不是"计划不好"，而是"环境变了但计划不改"。这在实际生产环境中暴露为：
- 文件系统状态变化导致路径失效
- API 返回格式变化导致后续步骤参数错误
- 中间结果不符合预期但执行器机械推进

**改良方案**：
- **Plan & Replan**（LangGraph 的思路）：每个关键步骤后检查前提条件是否仍成立
- **Checkpoint + Replan**：在计划的关键节点设置检查点，将当前状态提交给 Planner 决定是否修改后续计划
- **分级规划**：高级规划定方向（不轻易改），低级规划定步骤（可灵活调整）

#### Router + Skill 的路由准确性

Router 的准确性是单点故障源。当前业界实践：
- **意图分类 + 语义检索混合**：先用分类器缩小范围，再用向量相似度匹配最相关的 Skill
- **路由置信度阈值**：低于阈值的请求触发"歧义消解"——反问用户澄清意图
- **多路并行 + 仲裁**：发到多个 Skill 同时执行，由一个"仲裁者"选最优结果（成本高但容错好）
- **用户可见的路由日志**：让用户知道"AI 选择了哪个 Skill + 为什么"，方便纠偏（Claude Code 的做法）

#### Multi-Agent 的协调开销

N 个 Agent 不是 N 倍效果好。Agent 之间的通信、等待、冲突消解都有隐性成本。实际经验法则：
- **3-5 个 Agent 是效率/复杂度平衡点**：超过了收益递减明显
- **层级制 > 联邦制**（多数场景）：有一个明确的 Orchestrator 比让 Agent 自行协商高效得多
- **限制通信带宽**：不要每个 Agent 都跟每个 Agent 聊天，通过 Orchestrator 统一收发

#### Reflection 的有效条件

反思不是万能良药。反思有效的三个前提：
1. **有明确的成功标准**：代码能不能跑？数学答案对没对？没标准的任务是没法反思的
2. **模型本身能力够**：弱者反思自己的输出，看不出问题——这是"自我欺骗"
3. **外部反馈介入**：最有效的反思依赖外部信号（测试通过/失败、编译器报错、评分），纯粹自省的效果远不如外部验证

#### Tree of Thoughts 的成本

思维树在理论上非常优雅，在实践中非常昂贵：
- **BFS/DFS 探索的 Token 消耗是线性的 N 倍**
- 路径评估模型调用的边际收益递减——探索 5 条路径 vs 10 条路径，质量提升可能只有 5%
- **实际建议**：只在"一步走错全盘皆输"的高风险推理节点使用，不要全局开启

### 二、更优方案与设计模式

#### 实战推荐的混合架构组合

```
生产级 Agent = Multi-Agent (分工) + Router+Skill (调度) + Plan&Execute (主干) + ReAct (灵活节点) + Reflection (质量门)
```

具体层次：
1. **入站层**（Router）：接收任务，识别意图，路由到对应 Skill
2. **规划层**（Planner）：Skill 内部用 Plan & Execute 生成执行计划
3. **执行层**（ReAct Agent）：具体步骤用 ReAct 循环调用工具
4. **协作层**（Multi-Agent）：当 Planner 判断需要分工时，spawn 多个子 Agent
5. **质检层**（Reflection）：关键产出经过反思和自检再交付
6. **记忆层**（跨层）：每一步的经验存入记忆，供后续调用

这是 LangChain/LangGraph + Claude Code Skill 的工业级实践方向。

#### 什么时候不要用多 Agent

以下场景强行上多 Agent 是过度工程：
- **单一领域的线性任务**：如"把这篇 PDF 转成 Markdown"——一个函数调用就够了
- **延迟敏感的交互**：如实时对话——多 Agent 通信的延迟完全不可接受
- **成本预算严格**：每多加一个 Agent 就是多加一轮模型调用
- **调试资源有限**：找不到问题出在哪个 Agent 时，多 Agent 系统是噩梦

### 三、行业位置与趋势

**2026 年的 Agent 架构竞争格局：**

- **单 Agent 架构**已经不再被独立讨论——它变成了其他架构的"执行单元"
- **Workflow** 在被多 Agent 挤压，但在专业工具（ComfyUI、n8n）中地位稳固
- **ReAct** 是目前事实上的默认范式——几乎所有 Agent 框架的核心循环都是 ReAct 的变体
- **Plan & Execute** 在高可靠性场景（金融、合规）中被强制要求——你不能让 Agent 边想边做资金操作
- **Multi-Agent** 是 2026 年最热的架构叙事——"AI 团队"取代"AI 助手"的共识正在形成
- **Router+Skill** 是 Claude Code 生态带火的模式，正在被大量模仿
- **Reflection + Tree of Thoughts** 作为增强层，正从学术论文走向工程落地

**关键趋势判断**：
- 未来 2 年，Agent 架构将从"选一种"走向"组合多种"——就像软件架构从单体走向微服务再走向合理的混合
- **架构的透明性**（能解释为什么这么做）将成为竞争差异点——黑盒 Agent 不会被企业接受
- **架构的成本可预测性**将成为新的工程约束——"你猜这次任务多少 Token"的体验无法产品化

### 四、实操建议

1. **不要从零设计架构**：从现有框架起步（LangGraph、CrewAI、DeerFlow），先跑起来再优化
2. **从单 Agent + ReAct 开始**：这是最简单的有效起点。只有在明确遇到能力瓶颈时才加复杂度
3. **加 Multi-Agent 之前先做"任务拆解测试"**：手动拆解 10 个典型任务，看是否真的需要多人协作。大部分你以为需要"团队"的任务，其实一个 Agent + 好的 Skill 就能搞定
4. **Router+Skill 是性价比最高的模式**：投入产出比最好。Skill 可复用、可积累、可分享
5. **Reflection 是性价比第二高的增强**：给现有 Agent 加一个"检查你自己"的步骤，代码质量提升明显
6. **架构日志是调试救命稻草**：每个架构层次都要输出结构化日志——Router 选了哪个 Skill？Planner 生成了什么计划？ReAct 走了几步？Reflection 发现了什么？
7. **下一个视频预告**：按架构分类，逐个评估市面上的主流 Agent 工具各自的优劣和坑位

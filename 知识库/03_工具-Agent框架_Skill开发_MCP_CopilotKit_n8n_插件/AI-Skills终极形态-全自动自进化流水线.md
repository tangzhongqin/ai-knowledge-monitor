## 📌 一句话总结

**AI Skill 的本质是"按需加载的有组织知识包"，从单文件菜谱（1.0）到全自动生产线（6.0），六层进化对应着 Agent 从工具到工厂的跃迁——80% 的流程自动化不是梦，但绝大多数人卡在 2.0 的分层设计上。**

## 🔍 核心内容：AI Skills 六层进化全景

### Skill 的官方定义

> **"一组有组织的文件集合，为智能体打包和组合的流程性知识"**

四个关键词拆解：

| 关键词 | 含义 | 反模式 |
|--------|------|--------|
| **有组织** | 有主有次，有层级，不是一堆乱文件 | 所有文件平铺在一个文件夹 |
| **文件集合** | 多个文件协同工作，各司其职 | 一个超长 Prompt 塞进所有知识 |
| **可组合** | 技能之间可以像乐高一样拼接 | 技能之间硬编码耦合 |
| **流程性** | 封装的是"怎么做"的知识，不是"是什么" | 把百科知识当技能塞进去 |

**核心机制：按需加载（On-Demand Loading）** —— 像一个厨师，做宫保鸡丁只翻宫保鸡丁那一页，别的菜谱碰都不碰。SKILL.md 是"带路的"，不是"装货的"——问啥取啥，一次不用全加载。

### 1.0 做菜级别 —— 地基

```
做菜技能/
├── SKILL.md          # 只做一件事：带路（菜单 + 查找规则）
├── references/
│   ├── 红烧肉.md
│   ├── 宫保鸡丁.md
│   ├── 酸菜鱼.md
│   └── 土豆丝.md
```

- **模式**：一个岗位干一件事，简单直接
- **匹配场景**：单一领域的问答、格式转换、简单代码生成
- **Claude Code 对应**：单个 SKILL.md 文件，如 `/review` 命令

---

### 2.0 修车级别 —— 分层调用

```
修车技能/
├── SKILL.md                    # 先按车型分（品类少的那条线！）
├── _通用注意事项.md              # 人人必读：换轮胎、喷漆 — 不论什么车都先加载
├── 轿车/
│   ├── 通用做法.md
│   └── 专用做法.md
├── SUV/
│   ├── 通用做法.md
│   ├── 专用做法.md
│   └── 库里南.md               # 特殊车型单独建档
├── MPV/
│   └── ...
└── 房车/
    ├── 通用做法.md
    └── 尼莫克.md               # 特殊房车
```

- **关键判断**：**分类要挑"品类少"的那条线分** —— 修车按车型分（轿车/SUV/MPV/房车），品类少好管；按品牌分直接爆炸（几十上百个品牌）
- **模式**：先加载通用打底文件 → 进具体分支 → 特殊车型单独开小道
- **匹配场景**：多领域的工具使用、多框架的代码生成

---

### 3.0 外挂级别 —— 调用外部资源

**四条优先级链路**（真正的护城河）：

| 优先级 | 查找路径 | 实现方式 |
|--------|----------|----------|
| 1 | SKILL.md 带路 → 通用 references | 本地文件 |
| 2 | 通用没有 → 专用 references | 本地文件 |
| 3 | 专用也没有 → 自家知识库 | 向量数据库（ChromaDB/Pinecone） |
| 4 | 知识库还没有 → 联网搜索 | API 调用 / Web Search Tool |

**技术实现核心**：在 Skill 目录下新增 `scripts/` 文件夹，与 `references/` 同级：

```
技能/
├── SKILL.md
├── references/       # 静态知识
└── scripts/          # 对外接口：知识库查询、API调用、联网搜索
    ├── search_kb.py
    ├── web_search.py
    └── api_client.py
```

- **这个外挂不挑版本** —— 1.0 到 5.0，每一级都能挂知识库、挂查询、挂接口
- **匹配场景**：需要实时数据、外部 API、企业知识库的复杂技能

---

### 4.0 部门协同 —— 组织级技能

```
主控 Agent（拆任务 + 综合决策）
├── 子 Agent 产品部 → 独立上下文 → 只回传摘要
├── 子 Agent 设计部 → 独立上下文 → 只回传摘要
├── 子 Agent 财务部 → 独立上下文 → 只回传摘要
└── 子 Agent 流量部 → 独立上下文 → 只回传摘要
```

- **核心误区**：不是"一次性把所有部门文件全读进来再综合"——上下文窗口直接爆炸
- **正确做法**：每个部门派一个子 Agent 进独立上下文 → 只回传摘要 → 主控综合
- **类比**：医院多科会诊 —— 各科片子摆一桌，再综合下决策
- **匹配场景**：企业决策分析、复杂项目规划、多维度内容生产

---

### 5.0 统一入口 —— 超级大脑

```
用户需求 → [统一入口] → 自动判断分支 → 自动决定是否跨界借鉴
                ├── 造 SUV 部门
                ├── 造 MPV 部门
                ├── 造房车部门
                └── 造越野部门
```

- **类比**：好医院的分诊台 —— 你不需要自己判断该挂哪个科，分诊台自动路由，还能判断是否需要多科会诊
- **模式**：意图识别 + 自动路由 + 跨技能经验借鉴
- **匹配场景**：企业级 AI 中台、多功能 Agent 产品

---

### 6.0 自动化生产线 —— 终极形态

```
输入关键词/对标账号
    ↓
全网找同行的数据、下载视频    ← Skill A: 数据采集
    ↓
拆爆款、分析选题              ← Skill B: 内容分析
    ↓
写脚本                        ← Skill C: 脚本生成
    ↓
配图/生成素材                  ← Skill D: 素材制作
    ↓
剪辑/渲染                      ← Skill E: 视频剪辑
    ↓
输出成品
```

- **80% 的流程全部自动化** —— 你不需要一个一个组装技能，流水线已经编排好了
- **你是什么角色**：工厂老板，不是流水线工人
- **本质**：把 1.0-5.0 搭好的单个技能，编排成 DAG（有向无环图）工作流

## 🧠 专家升华

### 一、技术深度分析：六层架构背后的计算机科学

#### 1.0-2.0 的本质：从 Flat Retrieval 到 Hierarchical Routing

| 层级 | 计算机科学对应 | 具体实现 |
|------|---------------|----------|
| 1.0 | **Flat RAG** — 单一检索池 | 一个 SKILL.md 路由到 references/ 下的文件 |
| 2.0 | **Hierarchical RAG** — 分层检索 | 先按大类分 → 再分通用/专用 → 特殊单独处理 |
| 3.0 | **Agentic RAG with Tool Use** — 工具增强检索 | 本地查不到 → 知识库 → 联网，逐级 fallback |
| 4.0 | **Map-Reduce over Agents** — 分布式 Agent 推理 | 子 Agent 并行处理 → 主控汇总 |
| 5.0 | **Intent Classifier + Router** — 智能路由网关 | LLM 判断意图 → 自动分发 + 跨域借鉴 |
| 6.0 | **DAG Workflow Orchestration** — 有向无环图编排 | 多个 Skill 按依赖关系串联成流水线 |

**关键洞察**：这不是线性的"越来越好"，而是**每层解决不同量级的问题**。1.0 的扁平结构在处理 10 个菜谱时完全够用；2.0 的分层是应对品类爆炸的必然选择；3.0 解决了"本地知识不够"的问题；4.0 突破了"单 Agent 上下文窗口"的天花板。

#### 2.0 中"按品类分不按品牌分"的计算原理

选择"按车型分（4-5 个品类）"而不是"按品牌分（几十上百个）"的原因：
- **路由准确率**：LLM 在 4-5 个选项中的分类准确率 > 95%；几十个选项中可能降到 70% 以下
- **维护成本**：每增加一个品牌就要新增一个文件夹 + 文件，O(n) 增长
- **知识复用**：同车型的不同品牌，80% 的维修知识是共享的（通用打底文件）

**这本质上是一个分类树设计问题 —— 分支因子（branching factor）控制在 3-7 之间是最优的**，和 B+ 树的节点大小设计原理一致。

#### 4.0 子 Agent 独立上下文的必要性

这是一个被广泛忽视的架构决策。**为什么不把所有部门的文件一次性加载到主 Agent 的上下文？**

1. **上下文窗口碎片化**：假设每个部门文件 5K tokens，4 个部门 = 20K tokens。加上系统提示、对话历史，轻松超过 32K。模型在长上下文中容易出现"中间信息丢失"（Lost-in-the-Middle 效应）
2. **注意力稀释**：模型在 4 种不同领域的信息间切换，每个领域的推理深度都会下降
3. **成本指数增长**：输入 token 成本 × 上下文长度，4 个部门全加载的每次调用成本是单部门的 4 倍以上
4. **子 Agent 的"专家效应"**：独立上下文的子 Agent 可以携带专属的系统提示、工具、知识库，推理质量远高于一个"通才"上下文中处理所有事情

**正确做法就是 Map-Reduce**：每个子 Agent 在自己的专有上下文中深度推理（Map），主控只接收结构化的结论摘要进行最终决策（Reduce）。

### 二、更优方案：用你工具箱里的东西重构每一层

基于你的 CLAUDE.md 工具库，这是每一层的更优实现方案：

| 层级 | 原方案 | **更优方案** | 为什么更好 |
|------|--------|-------------|-----------|
| 1.0 | 手动 SKILL.md + references/ | **Claude Code SKILL.md** + 语义触发 | Claude Code 原生支持 Skill 自动加载，不需要手动指定 |
| 2.0 | SKILL.md 里的 if-else 路由 | **Embedding-based Router**（ChromaDB 做语义分类） | 不依赖 LLM 做路由，更快、更便宜、更准确 |
| 3.0 | 自定义 `scripts/` 文件夹 | **MCP Tools**（标准化接口） | MCP 是行业标准协议，可跨平台复用；scripts 是私有实现 |
| 3.0 知识库 | 自定义脚本查知识库 | **ChromaDB** (`localhost:8000`) + RAG | 向量相似度检索远优于关键词匹配 |
| 4.0 | 手动管理子 Agent 上下文 | **cc-fleet team**（长驻 Agent 团队） | 自动管理上下文隔离、消息传递、结果汇总 |
| 4.0 追踪 | 无 | **Langfuse**（调用链追踪） | 延迟、成本、成功率全链路可见 |
| 5.0 | LLM 意图判断 | **轻量分类器**（fastembed + 余弦相似度） | 比用 LLM 做路由便宜 100 倍，延迟降低 10 倍 |
| 6.0 | 手动编排 Skill 调用链 | **n8n** (`localhost:5678`) + **cc-fleet workflow** | 可视化拖拽编排 + 断点续跑 + 定时触发 |
| 安全 | 无 | **SkillSpector**（16 类风险、64 种检测模式） | 上线前自动扫描安全漏洞 |

#### MCP 替代 scripts/ 的具体方案

```
原方案（私有协议）:
技能/scripts/search_kb.py   → 只能在这个 Skill 里用

更优方案（MCP 标准）:
mcp__knowledge_base__search  → 任何 Skill、任何 Agent 都能调用
```

**实操**：把 `scripts/` 下的每个能力封装成独立的 MCP Server，然后在 `SKILL.md` 里声明依赖的 MCP 工具即可。这样做的附加收益：
- 跨 Skill 复用（写一次，到处用）
- 跨平台运行（Claude Code / Cursor / Codex 都能用同一个 MCP Server）
- 独立测试和版本管理

### 四、实操建议：别追求一步到 6.0

#### 正确的进化路径

```
第 1 步：从 3.0 开始（不是 1.0）
        ├── 原因：3.0（Skill + 知识库 + 联网）覆盖 80% 的实用性需求
        ├── 1.0-2.0 的按需加载和分层设计是 3.0 的基础，一并做好
        └── 耗时：1-2 天做出第一个可用的 3.0 Skill

第 2 步：当你有 5+ 个稳定的 3.0 Skill 时，才考虑 4.0
        ├── 原因：没有足够多的稳定 Skill，部门协同是空中楼阁
        └── 耗时：每个部门 Agent 调试 1-3 天

第 3 步：当多部门协作稳定运行 1 周后，加统一入口（5.0）
        ├── 原因：5.0 的路由准确率依赖你对用户意图的充分理解
        └── 耗时：路由逻辑调试 2-5 天

第 4 步：当你有明确的端到端业务流，才上自动化生产线（6.0）
        ├── 原因：6.0 是业务流程编排，不是技术炫技
        └── 耗时：每条生产线的编排 + 测试 1-2 周
```

#### 五个避坑指南

| 坑 | 表现 | 正确做法 |
|----|------|----------|
| **过早分层** | 3 个 Skill 就开始搞 4.0 部门协同 | 先打磨单个 Skill 质量，≥5 个再谈协同 |
| **分类维度选错** | 按品牌分（几十个）而不是按车型分（4-5 个） | 选"品类少的那条线"，分支因子 3-7 最优 |
| **SKILL.md 当仓库** | 把所有知识塞进 SKILL.md | SKILL.md 只做路由，知识放 references/ |
| **忽略 fallback** | 知识库查不到就报错 | 必须设 4 级降级链：通用→专用→知识库→联网 |
| **没有观测** | 上线后不知道哪个 Skill 慢、哪个总出错 | 第一天就接 Langfuse，全链路可观测 |

#### 从 0 到 1 做一个高级 Skill 的标准模板

```
my-skill/
├── SKILL.md                 # 路由规则：触发条件 + 分发逻辑
│   ├── 触发条件描述
│   ├── 分类树（分支因子 ≤ 7）
│   ├── 优先级规则
│   └── fallback 策略
├── references/              # 静态知识库
│   ├── _通用/               # 所有分支共享的打底知识
│   ├── 分支A/
│   │   ├── 通用.md
│   │   ├── 专用.md
│   │   └── 特殊情况.md
│   └── 分支B/
├── scripts/                 # 对外接口（建议迁移为 MCP Tools）
│   ├── kb_search.py         # 知识库查询
│   ├── web_search.py        # 联网搜索
│   └── api_client.py        # 外部 API
└── tests/                   # 测试用例
    ├── test_routing.md      # 路由准确性测试
    └── test_outputs.md      # 输出质量测试
```

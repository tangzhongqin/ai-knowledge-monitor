# 🧠✋ 一个管脑一个管手：Claude Code + Codex 最稳分工法

> 来源：抖音 | 收集时间：2026-07-23

---

## 📌 一句话总结

AI 编程的正确打开方式不是二选一，而是**角色分工 + 交接闭环**：Claude Code 当架构师（管脑），Codex 当施工队（管手），中间用标准化的任务清单和验收标准做交接，形成"规划 → 执行 → 验收"的闭环流水线。

---

## 🔍 核心内容

### 核心公式

```
Claude Code 规划 → Codex 执行 → Claude Code 再验收
    （大脑）          （手）          （眼睛）
```

### 三步分工法

**第一步：Claude Code 当架构师（管脑）**
- 负责**读项目**：理解项目结构、技术栈、已有代码逻辑
- 负责**拆需求**：把模糊的需求（"帮我做一个登录功能"）拆成可执行的任务
- 负责**定方案**：确定技术方案、架构决策、边界条件
- **关键输出**：任务清单 + 边界条件 + 验收标准

**第二步：Codex 当施工队（管手）**
- 负责**写代码**：按任务清单逐项实现
- 负责**改文件**：直接操作文件系统，修改、创建、删除
- 负责**跑命令**：安装依赖、运行脚本、启动服务
- 负责**处理报错**：遇到错误自行排查和修复
- **关键输入**：Claude Code 生成的结构化任务清单

**第三步：Claude Code 回来验收（闭环）**
- 看差异（diff review）：检查 Codex 改了哪些代码
- 跑测试：自动化测试是否通过
- 检查偏离：是否偏离了原定的架构方案
- 如果不满意 → 写修正清单 → 交回 Codex 返工

### 最关键的：交接格式

**不是丢一句话就完事了。** 交接格式决定协作质量：

| 交接要素 | 说明 | 示例 |
|----------|------|------|
| **任务清单** | 具体到文件级别 | "在 `src/auth/login.ts` 中实现 JWT 登录逻辑" |
| **边界条件** | 不能碰的区域 | "不要修改 `database/schema.ts`，只改 auth 模块" |
| **验收标准** | 怎么算做完 | "`npm test auth` 全部通过 + 登录接口返回 200" |

## 🧠 专家升华

### 一、技术深度分析：为什么这个分工有效

这不是简单的"一个人想一个人做"，而是利用了 **两种 AI 工具的架构差异**：

**Claude Code 的优势（适合规划与验收）**
- 强上下文理解：能读整个项目树，理解跨文件依赖
- 推理能力强：适合做架构决策、方案设计、trade-off 分析
- 内建 sub-agent 机制：天然支持任务拆分和编排
- 但操作桌面/GUI 能力弱：不能控制浏览器、不能操作非终端应用

**Codex 的优势（适合执行）**
- 桌面级操作能力：能控制鼠标键盘、操作任何桌面应用
- 执行速度极快：针对代码编辑、文件操作做极致优化
- 自带 Record & Replay：执行过程可录制、可重放
- 但全局理解不如 CC：在复杂多文件项目中容易"只见树木不见森林"

**本质**：这是 **Plan-Execute-Verify 架构** 在桌面 Agent 时代的落地实现。与你熟悉的 SWE-bench Agent（先理解 issue、再生成 patch、再跑测试验证）是同构的。

### 二、行业位置：当前 AI 编程工具的三种组织模式

| 模式 | 代表 | 适用场景 | 风险 |
|------|------|----------|------|
| **单兵模式** | 只用 Cursor / 只用 Codex | 简单任务、小项目 | 越改越乱，缺乏架构把控 |
| **分工模式** | **CC 规划 + Codex 执行**（本文） | 中大型项目、多人协作 | 交接成本高、需要规范 |
| **全自主模式** | Devin、Factory、自主 Agent | 明确界定的独立任务 | 不可控、结果不可预期 |

当前（2026 年 7 月）**分工模式是性价比最高、质量最可控的方案**。单兵模式太粗糙，全自主模式太不可靠。分工模式是"AI 编程的工程化"——类似从手工作坊到流水线的转变。

### 三、更优方案：CC+Codex 的 6 种接线方式升级

基于视频的"三步公式"，可以升级为以下 6 种接线方式（从简单到复杂）：

**方式 1：手动接力（本文基础版）**
```
你在 CC 中写任务清单 → 复制到 Codex → Codex 执行 → 回 CC 验收
- 优点：最简单，零配置
- 缺点：你来回复制，人工是瓶颈
```

**方式 2：MCP 桥接**
```
CC 通过 MCP 工具直接调用 Codex CLI → Codex 执行 → 结果回传 CC
- 优点：自动化交接，无需人工复制
- 需要：Codex CLI 暴露 MCP 接口
```

**方式 3：Sub-Agent 封装**
```
CC 创建 Codex 作为 sub-agent → CC 通过 task 工具发送任务 → sub-agent 中用 Codex 执行
- 优点：CC 原生支持，任务状态可追踪
- 实现：CC 的 task/agent 工具 + Codex CLI
```

**方式 4：Worktree 隔离**
```
CC 创建 git worktree → CC 在 worktree 中规划 → Codex 在 worktree 中施工 → CC 验收后 merge
- 优点：隔离性好，不会污染主分支
- 适合：实验性改动、大规模重构
```

**方式 5：n8n 编排流水线**
```
n8n 触发器 → CC API 规划 → 生成任务 JSON → Codex CLI 执行 → CC API 验收 → 通知
- 优点：全自动、定时触发、可视化监控
- 适合：CI/CD 集成、定时自动化任务
```

**方式 6：Record & Replay 固化**
```
先用方式 1 成功跑通一次 → Codex Record 录下来 → 之后类似任务直接 Replay
- 优点：重复任务零成本
- 适合：同类功能批量开发、回归任务
```

**推荐进阶路径**：方式 1（入门） → 方式 4（复杂任务） → 方式 3（日常） → 方式 5（自动化） → 方式 6（规模复制）

### 四、实操建议：好的交接清单怎么写

一个 Codex 能"无脑执行"的任务清单应该满足 **SMART-C** 原则：

- **S**pecific：具体到文件和函数名
- **M**easurable：有明确的验收方式（测试命令、预期输出）
- **A**tomic：每个任务独立可执行，不依赖上下文理解
- **R**estricted：明确边界，列出"不要碰"的文件或模块
- **T**estable：每个任务完成后有对应的验证命令
- **C**ontext-free：Codex 不需要额外上下文就能执行

**好清单 vs 差清单对比：**

| 维度 | 差清单 | 好清单 |
|------|--------|--------|
| 任务描述 | "优化登录性能" | "在 `auth/login.ts` 中，将 `bcrypt.compare` 改为异步调用，添加 Redis 缓存 token 验证结果（TTL=5min）" |
| 边界条件 | 无 | "不要修改 `auth/types.ts` 和 `middleware/auth.ts`，保持接口签名不变" |
| 验收标准 | "做好就行" | "`npm run test:auth` 全部通过 + `ab -n 1000` 登录接口 p99 < 200ms" |
| 上下文 | Codex 需要理解整个登录流程 | Codex 只需要知道改哪个函数、加哪种缓存 |

## 🔗 涉及工具

| 工具 | 角色 | 关键能力 |
|------|------|----------|
| **Claude Code** | 大脑（规划 + 验收） | 读项目、拆需求、定方案、diff review |

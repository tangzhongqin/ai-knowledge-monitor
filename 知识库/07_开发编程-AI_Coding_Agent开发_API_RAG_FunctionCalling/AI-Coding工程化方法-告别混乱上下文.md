# AI Coding 工程化方法：多 Agent 协作，告别超长混乱上下文

**来源**: 抖音 @AI编程实战 | 2026-07-23
**原始链接**: https://www.douyin.com/video/7659771506536450938

## 📌 一句话总结

把 AI 当"技术专家"而非"打字员"来用——用一个主控 Agent 拆任务、定接口、审代码、给反馈，三个子 Agent（前端、后端、UI）各司其职、通过 Git 分支协作，从"一条对话框用到死"升级为 AI 工程团队管理模式，彻底解决上下文膨胀和混乱问题。

---

## 🔍 核心内容

### 核心观念转型：一句话改变一切

> **不要把 AI 当成学员用，把它当成技术专家用。**

"学员模式"是你事无巨细地告诉 AI 每一步怎么做；"专家模式"是你告诉 AI 目标和约束，让它自己设计方案，你来审核结果。

### 多 Agent 协作架构

```
                 ┌─────────────┐
                 │  主控 Agent   │
                 │  (不写代码)    │
                 │              │
                 │ 1. 拆解任务   │
                 │ 2. 定义接口   │
                 │ 3. 审核代码   │
                 │ 4. 给出反馈   │
                 └──┬───┬───┬──┘
                    │   │   │
          ┌─────────┘   │   └─────────┐
          ▼             ▼             ▼
    ┌──────────┐ ┌──────────┐ ┌──────────┐
    │ 前端 Agent│ │ 后端 Agent│ │  UI Agent │
    │ (Vue/React│ │ (API/DB) │ │(样式/组件)│
    │  数据交互) │ │          │ │          │
    └──────────┘ └──────────┘ └──────────┘
```

### 主控 Agent 只干四件事（不写代码）

1. **拆任务** —— 把产品需求拆成可独立执行的前端/后端/UI 子任务
2. **定接口** —— 定义前端调后端的 API 契约（路径、入参、出参），各 Agent 按契约开发，不会跑偏
3. **审代码（Diff 审查）** —— 子 Agent 通过 Git 分支提交代码后，主控读 Diff 来审查，接受或驳回
4. **给反馈** —— 发现问题时明确告知子 Agent 哪里需要改、为什么

### 子 Agent 的工作机制

- 每个子 Agent 是**独立对话窗口**，互不干扰，各自专注自己的领域
- 前端只做数据交互和页面逻辑，后端只写 API 和数据库，UI 只负责样式和组件
- 它们之间**不直接通信**，通过 Git 分支代码和主控的接口契约实现间接协作
- 每个子 Agent 只处理分配给自己的任务，不会看到整个项目的全量上下文

### 协作流程

```
1. 主控 Agent 对话：拆解需求 → 定义接口 → 分配给各子 Agent
2. 子 Agent 各自开发 → 提交到自己的 Git 分支
3. 主控 Agent 读取各分支的 Diff → 审核代码 → 接受或驳回
4. 接受 → 合并分支；驳回 → 给出修改意见 → 子 Agent 修正
5. 每轮完成后，将本轮发现的坑/经验写入 Rules 文件
6. 下一轮各子 Agent 开始前，先读取 Rules 文件，避免重复犯错
```

### Rules 文件的持续积累

这是整个系统最关键的自进化机制：

- 每完成一轮开发，把遇到的坑、踩过的雷、总结的最佳实践记录进去
- "上次这里出了什么 Bug，原因是什么，下次注意什么"——这些经验沉淀为规则
- 下一轮开始时，每个子 Agent 先读 Rules，带着"历史教训"开始工作
- 日积月累，Rules 文件就是你的团队工程手册，AI 越用越聪明

## 🧠 专家升华

### 技术深度分析：这个架构为什么能真正解决问题

大多数 AI 编程工具的"一条龙"模式有一个根本缺陷：**上下文是人类时间的不可再生资源**。当你在一场对话里从需求分析聊到架构设计，从架构设计聊到前后端代码，从前后端代码聊到 Debug——上下文不断膨胀但永远不会收缩。到后期，AI 在回应你时，前面所有的对话历史（包括那些已经过时的、错误的、走了弯路的）都在它的"视野"里，这直接导致两个严重后果：

1. **注意力稀释** —— 模型对当前问题的注意力被历史对话分散，输出质量下降
2. **Token 钝化** —— 越往后，每次对话的成本越高（输入 Token 线性增长），越到关键时刻（快上线了、出 Bug 了）反而越贵

这套多 Agent 架构的精妙之处在于**用架构解耦替代了上下文清理**：

- **单一职责**：每个子 Agent 的上下文窗口里只有自己这个领域的事务，前端不会看到后端的数据模型细节，后端不会被前端的 UI 状态管理拖累。这本身就是一种上下文节流。

- **Git 分支做信息交换总线**：子 Agent 不直接对话，通过代码 Diff 交换信息。这确保了他们之间的"通信开销"是代码级别的，而非自然语言上下文级别的——一份 Diff 就是一份精确的结构化信息，没有歧义、没有废话。

- **接口契约作为"宪法"**：主控在任务分配前就定义好 API 接口，各子 Agent 按契约开发。这消除了传统多人协作里"你以为是返回数组，我实现成了返回对象"这种对齐成本——在 AI 编程里，这种"对齐偏差"会耗费大量上下文去解释和修正。

- **Rules 文件自进化**：这个机制让系统具备了学习能力。传统的 Rules 是人工一次性写好的死规则，而这套方法让 Rules 从实战中"长出来"——每次踩坑都变成一条新规则，越用越符合你的项目实际。

### 更优方案：从 4 Agent 到 N Agent 的演进路径

这套架构可以进一步深化：

1. **QA Agent（测试 Agent）** —— 增加一个专门写单元测试和集成测试的子 Agent。每次代码合并前，QA Agent 基于接口契约自动生成测试用例，先跑通再合并。把"主控审核"升级为"自动化测试 + 主控审查"双重质量门。

2. **Docs Agent（文档 Agent）** —— 当接口发生变更时，自动同步更新 API 文档。避免"代码和文档永远对不上"的经典问题。

3. **Architect Agent（架构 Agent）** —— 对于大型项目，主控先跟 Architect Agent 讨论架构方案（技术选型、数据库设计、部署策略），确定后再拆任务分发给子 Agent。这样主控不再承担架构决策的责任，专注于"拆任务、定接口、审代码"三项核心动作。

4. **从手动分配进化到自动化流水线** —— 当前方案是人工在不同对话窗口之间切换。远期可以结合 CI/CD：子 Agent 提交代码 → 触发 GitHub Actions → 自动跑 QA Agent 的测试 → 通过后通知主控审查 → 主控批准后自动合并。让"AI 工程团队"从半自动升级为全自动。

### 行业位置

这套方法论目前处于 **AI 编程工具使用方式的前沿**。大部分用户停留在"单对话全栈开发"阶段（这是工具默认支持的模式），少数进阶用户开始尝试"需求文档 → AI 实现"的工作流，而多 Agent 协作是更进一步的模式——它已经不是在"使用 AI 工具"，而是在"管理 AI 工程团队"。

这个模式对标的不是某个具体工具，而是一种**工程管理范式**。类比传统开发：初级程序员一个人全干（单 Agent），高级程序员用 AI 辅助自己（人+AI 协作），技术负责人管理一个 AI 团队（多 Agent 协作）。视频作者提到自己总结了"Codex 从入门到精通的 30 个实战经验"，说明这套方法论是在大量实战中反复打磨出来的，而非一次性灵机一动。

关键转折点：当项目复杂度超过单个 AI 对话能承载的上限时，多 Agent 架构就从"高级玩法"变成了"必要条件"。

### 实操建议

1. **从小项目开始练手** —— 先拿一个只有 3-5 个页面的小项目试这套流程，跑通后逐步放大。不要一上来就拿复杂项目试，容易因为流程不熟而放弃。

2. **接口定义要写在最开始** —— 主控在分配任务前，必须产出明确的接口契约文档（可以用 OpenAPI 格式，也可以简单的 Markdown 表格）。接口写得越清晰，子 Agent 跑偏的概率越低。

3. **Rules 文件要有结构** —— 不要写成流水账。建议分组：`[Bug 模式]`（以前出过的 Bug 特征和原因）、`[代码规范]`（项目特有的命名、格式约束）、`[架构约束]`（哪些表不能直连、哪些服务不能互相调用）。

4. **每个子 Agent 对话开新窗口，旧窗口不重开** —— 这是关键细节。如果子 Agent 在上一轮表现不好（产生了很多无效对话），直接开新对话窗口重新分配任务，不要在那个"污染过的"上下文里继续工作。

5. **主控也要定期"清零"** —— 当主控对话里的需求讨论超过 5 轮迭代时，考虑开一个新的主控对话，把"最终确定的需求 + 当前 Rules"贴进去，轻装上阵继续推进。

## 🔗 涉及工具

- **Claude Code / Codex / Cursor**（AI 编程工具，作为各 Agent 的运行载体）
- **Git**（代码版本管理 + 分支协作 + Diff 审查机制）
- **OpenAPI / Swagger**（接口契约的推荐格式）
- **GitHub Actions / CI/CD**（进阶方案：全自动化流水线）
